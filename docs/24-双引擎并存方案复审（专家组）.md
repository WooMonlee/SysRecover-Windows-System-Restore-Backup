# 24 · 双引擎并存方案复审（专家组）

> 日期：2026-10-11 / 版本：`0.7.24` / 触发：用户提问
> 「由于存在使用 Linux 兜底的情况，我们仍然得保留以前的那些功能 —— 这种并存的两种方案是否是最佳方案？」
> 结论：**方向正确（A 主 + B 备 = docs/23 D1 裁定维持）；但当前是"弱主备"—— 产品层缺降级引导，本轮补上 P1 三件。**

---

## 1. 背景与前提澄清

0.7 新架构：**A 引擎**（Windows 侧解压到 `<目标>:\~new` → Linux 救援层只做改名交换，不格式化）为默认；
**B 引擎**（0.6.x 旧线：Linux `mkntfs` 格式化 + `wimlib apply` 块写）经 `--engine block` 保留。

**前提澄清（写进矩阵，防误解）**：
- 「系统进不去」时的**主力兜底是 PE 就地还原**（`CanRestoreInPlace` → `RunDirectRestore`，`ops.cpp`；
  Windows 侧格式化 + apply + 修引导，不重启、不进 Linux）——不是 Linux 救援层。
- 开机菜单里的 SysRecover 项需要**已暂存的任务**；从未暂存过的机器进去是空壳 shell。
- B 引擎真正不可替代的场景见 §5 乙/戊两栏。

## 3. 五角色评审（要点）

| 角色 | 立场 | 核心论据 |
|---|---|---|
| 甲（架构） | A 主 B 备**方向正确**，但要做成"强主备" | A/B 是两种**空间语义**（可用空间 vs 总容量）而非两套功能，天然分层；缺的是产品层的**降级引导**（提示 + 显式选择 + 文档矩阵），不是功能合并 |
| 乙（售后） | 现场最怕"空间不够却不知道有后手" | 客户见 F4 报错会以为"要删数据/换盘"，实际 `--engine block` 只要总容量够就能跑；提示必须带下一条路（P1-1） |
| 丙（测试） | B 必须有常驻回归，否则 = 未测试代码 | F3 本次演练即 T6 落地；演练工具入仓 + `make drill`（P2-4），否则下个封存周期又会丢（0.6.54 曾移进 graveyard 致 ROOT 失效） |
| 丁（数据安全） | 静默组合 = 最大风险，宁可拒绝 | `keepOld × block` 若静默执行 = 用户以为有保护其实没有 → **fail-closed 拒绝**（P1-2）；同理未知 `--engine` 值拒绝（P1-1 附带） |
| 戊（竞品） | 保留 B = 保留差异点 | 易数/DiskGenius 等多为整盘/块级思路；A 引擎（解压不破坏目标、重启即交换）是我们的独特点，B 作兜底保住"低配机/坏盘也能救"的底线 |

## 4. 争议点

| 争议 | 甲说 | 乙说 | 裁定 |
|---|---|---|---|
| 是否该合并成一套引擎？ | 不合并，空间语义不同 | 现场只要"能救回来" | **不合并**（D1 维持）；补降级引导 |
| B 是否该默认参与 GUI？ | GUI 入口保持单一，避免误选 | 空间不够时客户找谁开 CLI？ | **本轮不进 GUI**（P2-5 留产品决策）；先靠 CLI 提示 + 文档矩阵 |
| 契约缺 `engine` 键当 block 合理吗？ | 兼容老任务，正确 | 老任务本来就是 block 语义 | 保持（0.6.x 老契约必需） |

## 5. 结论：A 主 + B 备并存 = 最佳方案（在补齐 P1 后）

B 引擎不可替代的场景（**保留的正当性**）：
1. 目标可用空间不足（A 需要"内容+页文件+余量"，B 只需"总容量 ≥ 镜像体积"）；
2. 目标分区文件系统损坏/非 NTFS（B 先 `mkntfs`）；
3. 现场无 PE 介质（B 免 PE）；
4. 0.6.x 旧契约（缺 `engine` 键 → 缺省 block）；
5. PE 认不出盘的机器（我们 494 模块的 Linux 可能反而能看到）。

A 引擎不可替代的优点（**主路的正当性**）：不格式化可备份旧系统（`~old` 备返）、不破坏非标布局、失败可回退、
还原后可 swap 回去（B 失败 = 已格式化，无回退）。
