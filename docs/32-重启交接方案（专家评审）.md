# 32 · 「重启进恢复环境」专家评审：穷举 → 收敛 → 方案（2026-10-31）

> 触发：0.9.67 在维护者本机暂存成功、重启却直接进旧系统（PIT-194）；此前还有客户机器在
> 重启环节反复翻车（PIT-193 的误报、PIT-192 的临时目录）。
> 结论：**不能再用"补丁式"修重启环节**，必须把它当成一条有 SLA 的**交接协议**来做。
> 本文 = 专家组评审记录（穷举 + 收敛）+ 落地清单。正文改动见 PIT-194 / PIT-195。

## 0. 参与视角（专家组构成）

| 角色 | 关注点 | 主要结论 |
|---|---|---|
| 固件/UEFI 专家 | BootNext/BootOrder/NVRAM/DevicePath 的兼容性 | **BootNext 不是可靠的交接机制**，只有 BootOrder 是各固件都认的 |
| Windows 引导专家 | bootmgr/BCD/bootsequence/bcdboot | BootNext 之外必须有一条"Windows 自己能验"的路径；bcdboot 不能当唯一出路 |
| Linux 救援层专家 | init/kernel/initramfs/自失效 | 救援层必须能"只用一次"，否则置顶启动项会把机器拉进死循环 |
| 产品/支持专家 | 用户看到什么、怎么自己恢复 | 失败必须"开机即报 + 给出两条可走的路"，不能静默 |
| 质量/可观测专家 | 判据、日志、回归 | 每一次交接都要有"写—读—验"三段证据，且能被下次启动读到 |

## 2. 收敛：四条原则 + 一张决策表

**原则（专家组一致同意）**

1. **不赌单一机制**：BootNext 只能当"加速"，**BootOrder 才是合同**。
2. **不确认不重启**：交接"写—读—验"不通过，宁可本次失败（目标零改动），也不让用户白重启。
3. **一次性 + 自失效**：任何"我们置顶的启动项"都必须能自己失效（删临时内核），杜绝死循环。
4. **失败必须可自愈**：下次开机自动清理残留启动项，并给出两条可走的路（手动选启动项 / PE 就地还原）。

**交接决策表（UEFI，Secure Boot off —— 主流路径）**

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 部署载荷；复制独立临时内核 `vmlinuz-zjtemp.efi` | 失败 → 回滚，不重启 |
| 2 | 写临时 `Boot####`（指向临时内核） | 失败 → 回滚，不重启 |
| 3 | **BootOrder 置顶** + 保存原序 `bootorder.bak` + 设 BootNext | 写失败 → 回滚，不重启 |
| 4 | 读回校验：条目在 + 临时内核在 + （BootNext 指向 或 BootOrder[0] 是它） | 失败 → 重写一次；仍失败 → **取消并提示**（不重启） |
| 5 | 进入救援层 | —— |
| 6 | 救援层**启动即删**临时内核（自失效） | 删不掉 → 记 WARN（下次开机自愈清理） |
| 7 | 新系统首启：删临时启动项 + 删 ESP 载荷 | 用户取消 → 下次开机自愈清理 |

**BIOS/MBR 路径**（保持 GRUB4DOS，但同样"不确认不重启"）
`grldr/grldr.mbr/menu.lst/bootsector` 四项 + `\ZJRESTORE\boot\*` 存在性与大小复核 +
`bcdedit /enum {临时GUID}` 回读 `device/path`，任一不符 → 取消、提示。

## 5. 回归判据（以后每次改这条链都要过）

1. 单元测试：`uefi_bcd_plan`、`bfp_*`（BootOrder 相关纯逻辑）。
2. 真机/VM：暂存 → 重启 → **必须**看到救援层横幅（否则视为失败）。
3. 人为把 `vmlinuz-zjtemp.efi` 删掉 → 再次重启必须回落 Windows（自失效有效）。
4. 人为把 BootNext 清掉 → 仍能进救援（BootOrder 置顶有效）。
5. 日志必须同时出现：`staged entry BootXXXX promoted to BootOrder[0]`、
   `boot state verified: BootXXXX ok (...)`。
