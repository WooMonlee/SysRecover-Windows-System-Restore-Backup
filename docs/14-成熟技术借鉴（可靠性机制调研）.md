# SysRecover · 成熟技术借鉴（可靠性机制调研）

> 用途：看看成熟系统（Windows 自身 / 嵌入式 OTA / Android A/B）在"把整套系统换掉"这类操作上
> 用了什么机制，哪些值得我们学、哪些不适用。
> 最后更新：2026-09-24（版本 `0.3.2`）。来源：Microsoft Learn（REAgentC / WinRE 技术参考）、
> Android A/B（source.android.com）、RAUC / SWUpdate / Mender 文档。

---

## 1. 结论先说

- 我们**已经在用**其中几项成熟机制（不是野路子）——见 §2。
- **3 项值得学**（§3），其中 **3.1 + 3.2 配套**能显著提升"还原失败后还能救回来"的能力。
- **1 项不适用**（§4）：整盘 A/B 双槽 —— 对整份 Windows 不现实，业界（Acronis / Image for Windows）
  在"整盘还原"上同样是"进恢复环境覆盖写"。

## 2. 我们已经在用的成熟机制（对齐确认，不是自创）

| 成熟机制 | 出处 | 我们的对应 |
|---|---|---|
| "下次启动进恢复" | Windows `reagentc /boottore`（本质是设 BCD `bootsequence`）| BIOS：BCD `bootsequence`；UEFI：`BootNext`（单次） |
| 常驻恢复入口 | Windows 硬件恢复按钮（`\EFI\Microsoft\Recovery` 二级 BCD + `/RecoveryBCD` + `BootOrder` 末尾条目）| UEFI：`Boot####` 挂 `BootOrder` 末尾 + ESP 常驻 `\EFI\ZJRESTORE\` |
| 动手前先验镜像 | 通用 | `WimEngine::Probe`（`WRITE_IN_PROGRESS` + 完整性）+ 空间预检 |
| 原子写（不留半成品）| 通用 | 备份先写 `<目标>.tmp`，成功才改名 |
| 签名引导 | shim / UKI / 微软 UEFI CA | 微软双签 shim → Debian 签名 GRUB/内核（零注册）|
| 卷级一致性快照 | VSS | wimlib `SNAPSHOT`（卷级，够用）|

> 也就是说：**"进恢复环境执行" + "单次启动" + "常驻入口" 这三件事，我们和 Windows 官方机制是一致的**。

---

## 3. 值得学（按价值排序）

### 3.1 ⭐ Windows 原生"两次启动失败自动进恢复"（BCD `recoverysequence`）
- **机制**：Windows 的 OS 启动条目带一个 `recoverysequence={WinRE-GUID}` 元素；满足 5 种条件之一
  （**连续两次启动失败**、两次异常关机、Secure Boot 错误、BitLocker 错误等）时，**bootmgr 自动改走恢复环境**。
  （WinRE Technical Reference 明确列出；注意：并没有 `winload /recovery` 这种开关，全靠 BCD。）
- **能学什么**：还原成功后，把**还原出来的 Windows** 的 `recoverysequence` **指向我们的救援条目**
  （UEFI 下救援常驻 ESP）。于是"**还原成功但起不来**"时，用户**不需要任何外部介质** ——
  开机失败两次就自动回到我们的救援，可再还原一次。
- **成本**：中（改目标 BCD + 让救援支持"失败重入"）；**价值：高**（把"变砖"变成"可自救"）。
- **前提**：救援重入必须**防循环**（否则失败就反复还原）→ 靠 §3.2 的"成功标记"。

### 3.2 ⭐ "启动成功标记"（Android A/B `markBootSuccessful` / RAUC `mark-good`）
- **机制**：新系统启动后由用户态**标记为 good**；启动失败达到重试次数则由 bootloader **自动回滚到旧槽**。
- **能学什么**：还原后放一个"**待确认**"标记；**首次成功进入 Windows 后清掉它**（计划任务 / RunOnce）。
  若下次开机标记仍在（= 上次没成功进入），则救援接管。这就是**单槽版的 A/B 回滚**，且**不占双倍空间**。
- **成本**：中；**价值：高**。

### 3.3 BIOS 下的"常驻救援"（Windows 恢复分区模型）
- **机制**：Windows 把 WinRE 放在**独立恢复分区**（固定 GPT Type ID `DE94BBA4-…`），C: 坏了也能进恢复。
- **我们的差距**：**BIOS 路径**把救援文件放在目标分区（C:，PIT-059），**格式化后就没了** →
  失败重试**必须有外部介质**。（UEFI 已常驻 ESP ✓；且单次运行中内核在内存里，**同一次开机内可重试** ✓。）
- **能学什么**：BIOS 下也留一份**小的常驻救援**（独立隐藏分区；或数据盘 `ZJRESTORE` + BCD 指向它）。
- **成本**：高（分区规划）；价值：中（只对 BIOS 老机器）。

---

## 4. 不适用：整盘 A/B 双槽

- A/B 的价值是"**保留旧槽可回滚**"，代价是**双倍空间**。整份 Windows 双份不现实；
  业界对"整盘还原"（Acronis / Image for Windows / 易数）同样是"**进恢复环境覆盖写**"——
  **我们与业界一致**，这不是落后，而是问题性质决定的。
- 真正的可靠性提升靠 §3.1/§3.2 的"**可自救**"，而不是双槽。

---

## 5. 建议

**先做 §3.1 + §3.2（配套）**：
1. 还原成功后，给目标 Windows 的 BCD 加 `recoverysequence` → 指向我们的救援条目（UEFI 优先）。
2. 放一个"待确认"标记；首次成功进 Windows 后清除（RunOnce / 计划任务）。
3. 救援侧：检测到"待确认标记仍在"时**不再自动重跑还原**，而是进入交互/重试提示（防循环）。

效果：**"还原失败 = 变砖" → "还原失败 = 开机两次后自动回救援，再试一次"**。

§3.3（BIOS 常驻救援）视需求再上。
