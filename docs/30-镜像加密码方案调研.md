# 镜像加密码方案调研（2026-10-28）

> 需求：用户希望"对镜像实施加密码"——备份产物落盘后，**没有密码就无法还原/读取**。
> 状态：**调研结论**（未实现）。实测数据与代码事实见下；所有"可做/不可做"都标注了依据。

## 1. 结论摘要（先看这段）

1. **WIM/ESD 本身没有加密能力**：`wimlib.h` 里只有"遇到加密段就报错"的
   `WIMLIB_ERR_WIM_IS_ENCRYPTED = 74`，**没有任何设置密码 / 解密 的 API**。
   所以"给镜像加密码"只能靠**我们自己包一层容器**。
2. **建议分三阶段**，先做能立刻交付、风险最小的：
   - **P0（零代码，立刻可用）**：引导用户把镜像放在 **BitLocker / VeraCrypt 加密卷**上。
     我们不写一行加解密代码，安全边界由成熟产品保证；缺点是要用户会建加密卷。
   - **P1（推荐实现）**：自有容器 `ZJENC1`（AES-256-GCM 分块 + PBKDF2-SHA256），
     **只在 Windows 侧解密** → 备份、校验、**A 引擎（解压并安装）/ PE 就地还原**全支持；
     **B 引擎（重启进 Linux 直接 apply）暂时明确拒绝**并给出替代路径。
   - **P2（按需）**：要让 B 引擎也能还原加密镜像，需给救援层加解密通道
     （`dm-crypt`+`cryptsetup`，或 `openssl` 解密到临时文件 —— **要占等量空间**），
     体积/复杂度都上一档，见 §5。
3. **有一处硬冲突必须先说清**：**「安装到启动」的常驻菜单 + 加密镜像 = 无解**
   （还原发生在开机阶段，没人输入密码）。建议：**加密镜像禁止安装常驻菜单**，
   只允许"解压并安装 / PE 就地还原"这种**当场输入密码**的路径。

## 2. 现状与约束（决定了方案形态）

| 事实 | 依据 | 对方案的影响 |
|---|---|---|
| wimlib 无加密 API | `third_party/wimlib/wimlib.h`：只有 `WIMLIB_ERR_WIM_IS_ENCRYPTED=74` 与"reads encrypted segments"错误说明 | 只能"外层容器"，不能改 WIM 内部格式 |
| wimlib 需要**随机访问**镜像文件 | 它按块/资源表 seek 读取（不是顺序流） | 容器必须支持**按块随机解密**，不能做"整文件 CBC 流"（解密到临时文件除外） |
| 救援层当前没有解密工具 | `tools/build-debian-rescue.py`：`kernel/crypto/` 在白名单内，但 **`kernel/drivers/md/`、`cryptsetup` 都不在** | Linux 侧解密 = 要新增模块 + 二进制（体积 ↑） |
| 救缓层是 busybox + musl，无 GUI | `bootfiles/alpine/init` + `zjrestore-lite.sh` | 密码只能从控制台输入（有键盘/串口时） |
| 加密镜像的**常驻菜单**在开机阶段执行 | `StageRestoreMenu` → 契约 `image_path` | **无人可输密码** → 必须禁止或额外存密码（不可接受） |
| Windows 侧有 AES-NI 可用 | BCrypt（`BCRYPT_CHAIN_MODE_GCM` + `BCryptDeriveKeyPBKDF2`） | 备份时加密 ≈ 内存拷贝速度（GB/s 级），PBKDF2 600k 约 0.3~0.6 s |

## 3. 候选方案对比

| 方案 | 做法 | 优点 | 缺点/风险 | 结论 |
|---|---|---|---|---|
| **A. 自有容器（Windows 侧解密）** | 备份完成后把 `.esd/.wim` 包成 `.zje`；还原/校验前在 Windows 侧解密（A 引擎解压时边解边写，PE 就地同理） | 零新依赖、AES-NI 快、**A 引擎/PE 全通** | **B 引擎不能还原**（Linux 读不了）；含 ESP/EA 子镜像时尚需处理（见 §6） | ✅ **P1 推荐** |
| B. 自有容器 + Linux 解密（openssl 到临时文件） | 救援层先用 `openssl` 解密成明文再 apply | B 引擎也能还原 | **需要等量空闲空间**（20GB 镜像就要 20GB）、耗时≈读+写一遍、要带 openssl 二进制（musl 静态约 +1MB，含 libcrypto 更大） | ⏳ P2 备选 |
| C. 自有容器 + Linux `dm-crypt` | loop 加密镜像 → `cryptsetup` 映射成块设备 → wimlib 直接读 | 无额外空间、随机访问、性能好 | 需 `dm-mod/dm-crypt` 模块 + `cryptsetup`（+1~2MB）、内核配置要能建 loop、密码交互 | ⏳ P2 更优（若必须 B 引擎） |
| D. 7z / ZIP AES | 用现成加密压缩格式 | 生态成熟 | 引入 GPL 组件或大依赖；7z 对超大流式文件不友好；还需 Linux 侧 7z | ❌ 不采用 |
| E. 系统加密卷（BitLocker/VeraCrypt） | 镜像放加密卷 | **零代码**、成熟安全 | 需要用户建卷；还原时卷要解锁（PE 里要么带驱动/要么先解锁） | ✅ **P0 立刻可用** |

## 4. 推荐方案（P1）的格式与实现

### 4.1 容器格式 `ZJENC1`（草案）

```
Header(固定 64B)：
  magic     "ZJENC1\0"           8B
  version   1                    u32
  kdf       PBKDF2-HMAC-SHA256   u32
  iters     600000               u32
  chunk     1048576 (1 MiB)      u32
  plainSize 原始镜像字节数        u64
  salt      [16]B
  nonceBase [8]B                 （每块 nonce = nonceBase || chunkIndex(LE32)）
Body：每块 = 密文（=明文块长） + tag[16]
```

- **AES-256-GCM**（认证加密）：篡改/截断会被发现（比 CBC+HMAC 少一层手写）。
- **1 MiB 分块**：支持随机访问；崩溃续写可按块边界；内存占用恒定。
- AAD = `chunkIndex`（防块重排）。

### 4.2 密钥派生

- `PBKDF2-HMAC-SHA256(password, salt, 600000) → 32B`；salt 随机 16B 存 header。
- 口令长度建议 ≥ 8；**不做密码提示字段**（提示=泄露），界面上写明"忘记密码无法恢复"。

### 4.3 接口（与现有链路对齐）

| 场景 | 行为 |
|---|---|
| `backup --password <pwd>` / GUI 勾选"加密备份" | 先写 `<dest>.tmp`（现状），再加密成 `<dest>.zje`，删除明文（或直接边写边加密，P2 优化） |
| `verify` / `images` | 检测 `.zje` 后缀 → 要求密码 → 临时解密头部块读元数据（不落盘明文） |
| 还原（A 引擎 / PE 就地） | 需要密码 → 解密后按现有流程解压/还原 |
| 还原（B 引擎，重启进 Linux） | **拒绝**：`加密镜像只能用「解压并安装」或 PE 就地还原`（现有 `rc=4` 门禁体系可直接复用） |
| 「安装到启动」常驻菜单 | **拒绝**（无人输密码），提示改用"解压并安装" |
| `extract`（取单个文件） | 需要密码（同 verify 路径） |

### 4.4 Windows 实现要点

1. `BCryptOpenAlgorithmProvider(BCRYPT_AES_ALGORITHM)` → `BCRYPT_CHAINING_MODE = BCRYPT_CHAIN_MODE_GCM`。
2. `BCryptDeriveKeyPBKDF2(BCRYPT_SHA256_ALGORITHM, …)` 派生 32B 密钥（600k 迭代）。
3. 逐块 `BCryptEncrypt/BCryptDecrypt`（含 `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO`）。
4. 进度走现有 `ProgressFn`；产物 `.tmp + rename`（与现有原子写一致）。
5. 密码只放内存（`SecureZeroMemory` 清理），不写日志/契约/history。

### 4.5 需要改的模块

`src/common/crypt.{h,cpp}`（新）＋ `WimEngine` 之上加"读层"（`ZjeReader`），
`ops.cpp` 的 `RunBackup/RunDirectRestore/StageRestoreImpl/RepairBoot(不涉)` 接线，
`task.cpp` 契约**新增增量键** `image_enc=1`（不升 contract_version；救援层读不到就按明文处理 → 但要拒绝）。

## 5. P2：让 B 引擎也能还原加密镜像（两条路）

| 路线 | 增量体积 | 额外空间 | 速度 | 复杂度 |
|---|---|---|---|---|
| openssl 解密到临时文件 | `openssl`(+libcrypto) ≈ 3~6MB（静态更大） | **= 镜像大小** | 读+写一遍（20GB ≈ 2~4 min） | 低（脚本改动） |
| dm-crypt + cryptsetup | 模块 ~200KB + `cryptsetup` ~1MB | 0 | 接近原生（AES-NI） | 中（内核模块白名单、loop 设备、密码交互、卸载清理） |

**倾向 dm-crypt**：不占空间、性能好；代价是要把 `kernel/drivers/md/dm-{mod,crypt}.ko*` 加进
`build-debian-rescue.py` 的白名单（并扩展构建期断言），并确认 `/dev/loop*` 可用。

## 6. 与现有两条链路的冲突点（必须一起设计）

1. **ESP / EA 子镜像**：A 引擎主 payload 由 Windows 解压（OK），但**ESP/EA 子镜像目前是 Linux 侧 apply**
   （`zjrestore-lite.sh` 用 `$WIMLIB apply "$IMG_FILE" …`）→ 加密镜像这条会读不了。
   解决（择一）：① 暂存时由 Windows 侧把这两个子镜像解到 `ZJRESTORE\espfix|eafix\`，Linux 只做拷贝；
   ② 只允许"无 ESP/EA 子镜像"的镜像加密（并在备份时提示）。
2. **常驻菜单**：见 §1.3 —— 加密镜像必须禁止（或在装菜单时要求"另存密码文件"，
   但那等于把钥匙放在旁边，不做）。
3. **PE 里就地还原**：可行（Windows 侧解密），要保证 PE 里有我们的 exe + 密码输入（GUI 可用）。
4. **忘记密码**：无任何后门，只能重新备份。UI 必须写死这句。

## 7. 工作量与验证清单（P1 估算）

| 项 | 估算 |
|---|---|
| `crypt.cpp`（PBKDF2 + GCM 分块读写 + 自检向量） | 1 天 |
| 备份/校验/还原接线 + 契约增量键 + 门禁拒绝 | 1 天 |
| GUI 密码框 + CLI `--password` | 0.5 天 |
| 单测（RFC 6070 PBKDF2 向量、GCM 向量、错密码/篡改/截断 fail-closed） | 0.5 天 |
| 端到端（备份→校验→A 引擎还原→PE 就地还原；B 引擎拒绝提示） | 0.5 天 |

验证要点：① 错密码/篡改 1 字节/截断 → 一律拒绝且**不写目标分区**；② 20GB 镜像加密
吞吐 ≥ 500MB/s（AES-NI）；③ 密码不落日志（`grep` 验收）；④ 加密镜像走 B 引擎必须 `rc=4`。

## 9. 追加评估：用户提议的"外壳头 + 修改原镜像头"（2026-10-28）

用户提议：*"加密方式使用 P1，是否可以为镜像添加一份『外壳』头，并修改原有的头部信息，这样就可以兼容 Linux 下的恢复了"*。

**结论：外壳头该做，但它不能替代 Linux 侧的解密器。**

1. **可以做的（也就是我们要做的）**：在加密容器开头放**明文**头（`ZJENC1` + 版本 + KDF 参数 +
   salt + 分块大小 + 明文长度）。好处：
   - Linux 侧能**认出这是加密镜像**（而不是把乱码当损坏镜像），能**立刻给出准确提示**
     （"需要密码，请用 PE / 解压并安装"），也能据此算"解密后要多少空间"；
   - 未来若加 Linux 解密器（P2），它拿到头就能按块随机解密，无需扫描全文件。
2. **不能做的**：修改 **WIM 自己的头**（前 208 字节 `MSWIM\0\0\0`、header flags、资源表指针）
   **没有任何收益**，反而有害：
   - wimlib 会校验 magic/flags/资源表偏移，改了就 **open 失败**（Windows 侧我们自己也读不了）；
   - 即便改了头，**文件数据仍是密文**，Linux 的 wimlib 依然无法 apply —— 头明文 ≠ 数据可读；
   - 系统里的 DISM/7-Zip 等工具也会因此拒读这个 .wim。
   → 所以**加密层必须在 WIM 之外**（`.zje` 容器），WIM 文件本身保持原样（这样也能用第三方工具校验）。
3. **关于"加密前先扫描、不具备 Linux 恢复条件就不允许重启后还原/装菜单"**：规则要更精确，
   因为重启后还原有**两条引擎**（`docs/25` PIT-064/PIT-138）：

   | 引擎 | 谁读镜像 | 加密镜像能否用 | 说明 |
   |---|---|---|---|
   | **A 引擎（解压并安装）** | **Windows 侧**解压 `~new` | ✅ 可以 | 密码在 Windows 界面里输一次，重启后 Linux 只做目录交换 |
   | **B 引擎（扫描后安装 = block）** | **Linux 侧** wimlib apply | ❌ 不行（P1） | Linux 没有解密器；要支持得做 P2 |
   | **PE 就地还原** | Windows 侧 | ✅ 可以 | 与 A 引擎同理 |
   | **「安装到启动」常驻菜单** | 开机阶段 Linux | ❌ **必须禁止** | 那一刻没人能输密码（除非把密码存本地 = 等于没加密） |

   → 推荐矩阵：**加密镜像默认走 A 引擎/PE**；`扫描后安装`（B 引擎）直接拒绝并说明原因；
   `安装到启动` 拒绝（无论镜像是否有 EFS）。**"扫描"仍保留**：它决定"这个镜像能不能用 B 引擎"，
   对加密镜像而言结论恒为"不能"，所以加密时不必强制扫描，只需在**选择路径时**按上表拒绝。
4. **ESP / EA 子镜像（必须先解决，否则 A 引擎也会卡）**：这两个子镜像目前由 **Linux** apply
   （`zjrestore-lite.sh` 用 wimlib 读同一个镜像）→ 加密后读不了。二选一：
   - **推荐**：暂存阶段由 **Windows** 把 ESP/EA 子镜像解到 `ZJRESTORE\espfix|eafix\`，
     Linux 只做"拷贝到 ESP / 投放 EA 载荷"（纯文件操作，不碰镜像）；
   - 简化：加密镜像**不允许包含 ESP/EA 子镜像**（备份时提示"加密镜像请取消勾选『同时备份ESP』"）。
5. **一句话**：外壳头 + 明文元数据 = 正确设计；真正的门槛是"**Linux 侧没有解密能力**"，
   所以 P1 的边界就是"加密镜像只能在 Windows 侧被读取"。
