# SysRecover · 32 位支持评估（待实施）

> 状态：**已评估、待实施**（2026-09-20 用户决定"等几天再说"）
> 结论先说：**体积几乎不用担心；速度只在"备份 + 重压缩"时吃亏，还原完全不吃亏。**

## 0. 决策与结论（2026-09-24 更新，版本 0.3）

用户明确：**目标机器 CPU/主板都是 64 位**，只是**系统**可能是 Win7 x64 甚至 **Win7 x86**；
**不考虑真正的 32 位 CPU 老机器（已过时）**。所以本项需求 = **让 Windows 侧 exe 能在 32 位系统上跑**，
**救援层（Linux，x86_64）完全不动**。

### 0.1 为什么救援层不用动
还原在 Linux 救援层执行，救援内核是 **x86_64**，需要 64 位 CPU —— 而目标机器 CPU 都是 64 位 ✓。
所以"32 位 Windows + 64 位 CPU"这种最常见情形，**现有 x64 救援层照常工作**，只有 Windows 侧 exe 需要变成 x86。

### 0.2 会损失什么（x86 单包 vs 现在的 x64）
| 项 | 影响 |
|---|---|
| Win7 x86 / Win10 x86 能否运行 | **从"完全不能"→"能"**（收益）|
| WinPE | 32 位 exe 在 32/64 位 PE 都能跑（收益）|
| **备份压缩速度** | **唯一的实质损失**：`recovery`(LZMS) ≈ −20~35%，`maximum`(LZX) ≈ −10~20%，`fast`(XPRESS) ≈ 0~10% |
| 还原速度 | **0%**（Linux 侧做，与 exe 位数无关）|
| 内存寻址 | 32 位进程上限 2GB（64 位系统上开 `LARGEADDRESSAWARE` 可到 4GB）；超大镜像极限压缩可能受限 |
| 功能完整性 | **无损失**（设备 IO / BCD / VSS / wimlib 都支持 32 位）|
| 64 位 Windows 用户 | 除"备份压缩慢一点"外**无损失** |

> **想做到"零损失"→ 方案 C**（x86 + x64 两套 + 启动器，按系统位数自动选）：64 位系统用 x64 全速，
> 32 位系统用 x86。体积只 +4MB（救援层占 90%，Windows 侧翻倍也就这点）。见 §2/§6。

### 0.3 Win7 x86 的引导特性（好消息）
Win7 **x86 不支持 UEFI**（只有 Win7 x64 支持）→ Win7 x86 必然走 **BIOS/MBR + GRUB4DOS**，
正好是我们最成熟、已验证的路径 ✓。**不需要** `shimia32.efi` 等 IA32 UEFI 资产。

### 0.4 为什么不考虑"32 位救援层"
- 现有救援底座 **Debian 13 已取消 i386 内核**（官方原文：*"i386 is no longer supported as a regular
  architecture: there is no official kernel and no Debian installer for i386 systems. The i386
  architecture is now only intended to be used on a 64-bit (amd64) CPU."*）。
- 且目标机器 CPU 都是 64 位 → x86_64 救援内核照常启动 ✓，**没有做 32 位救援层的必要**。

### 0.5 实施进度（2026-09-24，`0.3.2`）

  （**独立输出** `build-x86/` + `dist-x86/`，x64 完全不受影响，两套共存：`mingw32-make -f Makefile ARCH=x86 package`）；

## 1. 为什么会有这个需求

2026-09-20 用户实测：在 **32 位 Windows 7** 上运行本程序出错 —— 原因是**目前只出 x64**，
而 **x64 exe 在 32 位系统上由系统层面直接拒绝**（"不是有效的 Win32 应用程序"），
**程序内没有任何机会提示** ✗。所以要么出 32 位版，要么在下载页写明"仅 64 位"。

## 2. 体积（基于实测）

当前 `dist`（2026-09-24 实测，含 PIT-079 模块裁剪）：

| 部分 | 大小 | 占比 |
|---|---|---|
| Windows 侧（x64）：`SysRecover.exe` 1.31 + `SysRecoverUI.exe` 2.14 + `libwim-15.dll` 0.47 | **3.92 MB** | **10.0%** |
| 救援层（内核 + initramfs + GRUB/shim，**与位数无关**）| **35.06 MB** | **89.8%** |
| 合计 | **39.06 MB** | 100% |

加 32 位后的增量：

| 方案 | 增加什么 | 增量 | 新 `dist` |
|---|---|---|---|
| **B**：x86 主体 + **x64 只做备份** | x86 全套（3.92MB）+ x64 **只留 CLI**（1.31+0.47），去掉 x64 GUI（−2.14）| **+1.8 MB** | **≈40.9 MB（+4.6%）** |
| **C**：两个完整版 + 启动器 | x86 全套 + x64 全套 + 启动器 | **+4.0 MB** | **≈43.1 MB（+10%）** |
| （对照）只出 x86 | 换成 x86 一套 | ≈0 MB | ≈39.0 MB |

> **救援层占了 93%，所以加一套 Windows 程序对总体积几乎没影响** ✓
> 下载包（zip）约再 +1~2 MB。

## 3. 速度（只有"备份"受影响）

备份 = 读盘 + **压缩** + 写盘；32 位的劣势只在压缩这一段，且取决于算法：

| 备份算法 | 瓶颈 | 32 位相对 64 位 |
|---|---|---|
| `--compress fast`（XPRESS，很快）| **磁盘** | **≈0~10%** 慢（几乎无感）|
| 默认 / `maximum`（LZX）| CPU 与磁盘各半 | **≈10~20%** 慢 |
| `--compress recovery`（LZMS，最省空间）| **CPU** | **≈20~35%** 慢 |

- **还原：0%** ✓（格式化 + apply 由 Linux 救援层完成，与宿主 exe 位数无关）
- 量级示例（30GB、SSD）：`fast` 3.5min → 3.6~3.9min；`recovery` 12min → 15min
- 用户结论：**15 分钟变 18 分钟可以接受** ✓
- ⚠️ 以上为**区间估计**，非实测（本机无 i686 工具链）；装好后可做 A/B 实测补真实数字

## 4. 实施前置条件（四样）

1. **i686-w64-mingw32 工具链**（另装一套 MinGW；用户侧）
2. **官方 32 位 `libwim-15.dll`**（wimlib 同时发布 `windows-i686` / `windows-x86_64` 包 ✓，官方原话 "both fully supported, but prefer 64-bit as noticeably faster"）
3. **Makefile `ARCH=x86` 分支**（我方；含 rc/manifest 的 x86 编译，保持 `_WIN32_WINNT=0x0601`）
   - ⚠️ **两个 `libwim-15.dll` 同名，不能放同一目录** → 需分目录（如 `x64\`）或用启动器布局
   - 方案 B 需"32 位 GUI 起 x64 子进程做备份"，进度经 `progress.json` 轮询（机制已有 ✓）
   - 方案 C 更规整：两个完整 exe + 极小启动器按系统位数选择，**无跨进程**
4. **x86 版 UCRT**（Win7 没有 UCRT；`third_party/ucrt/x86/` 放 `ucrtbase.dll` + `api-ms-win-crt-*.dll`，
   `make package` 随包，约 1.5MB）。**不做这步 → Win7 x86 报"缺少 DLL"**（Win7 x64 同理，见该目录 README）

### 4.1 WOW64 细节（32 位 exe 跑在 64 位 Windows 上）
- **System32 重定向**：32 位进程 `GetSystemDirectoryW` 得到 `SysWOW64`。`bcdedit/bcdboot/manage-bde/format.com`
  在 SysWOW64 里大多有，但为稳妥应改用 `Wow64DisableWow64FsRedirection` 或 `Sysnative` 取**原生** System32。
- **注册表重定向**：32 位进程访问 `HKLM\SOFTWARE\...` 会被重定向到 `WOW6432Node`。
  `src/common/sysinfo.cpp` 已用 `KEY_WOW64_64KEY` ✓；`src/disk/disk.cpp` 那处注册表读取需复核。
- **VSS**：只用**卷级快照**（不需应用一致性）→ 不受影响 ✓
- **功能无缺**：`DeviceIoControl` 读盘、`bcdedit`、`libwim` 均有 32 位版本 ✓

## 5. 不受影响 / 注意点

- **救援层与宿主位数无关** ✓（Linux 侧照旧）
- **BIOS + GRUB4DOS** ✓ 与位数无关
- **UEFI 引导资产是 x64**（`shimx64.efi` + 64 位内核）→ 注意"**32 位 Windows 装在 64 位 UEFI 机器上**"
  是**普通情况** ✓，我们的资产照用 ✓；只有极罕见的 **32 位 UEFI（IA32）** 才需要 `shimia32.efi` + 32 位内核 ✗
- **PE**：32 位 PE 只能跑 x86 ✗ → 若做方案 C，启动器需能识别并选 x86；`fast` 压缩下速度差异很小 ✓
- VSS：32 位进程在 64 位系统上看不到 **64 位 VSS writer**，但我们只用**卷级快照**（不需要应用一致性）✓ 不受影响

## 6. 建议的落地方式

- 若 32 位客户占比不高 → **只出 x86**（一个包通吃，只亏备份那点速度）
- 若常备份大系统 + 64 位机器为主 → **方案 C**（两个完整版 + 启动器，比 B 少一层跨进程）
- 若 32 位客户几乎没有 → 维持 x64，并在**下载页/说明**里写明"仅 64 位"
