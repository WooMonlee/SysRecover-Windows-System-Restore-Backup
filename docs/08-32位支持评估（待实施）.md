# SysRecover · 32 位支持评估（待实施）

> 状态：**已评估、待实施**（2026-09-20 用户决定"等几天再说"）
> 结论先说：**体积几乎不用担心；速度只在"备份 + 重压缩"时吃亏，还原完全不吃亏。**

---

## 1. 为什么会有这个需求

2026-09-20 用户实测：在 **32 位 Windows 7** 上运行本程序出错 —— 原因是**目前只出 x64**，
而 **x64 exe 在 32 位系统上由系统层面直接拒绝**（"不是有效的 Win32 应用程序"），
**程序内没有任何机会提示** ✗。所以要么出 32 位版，要么在下载页写明"仅 64 位"。

## 2. 体积（基于实测）

当前 `dist`（2026-09-24 实测，含 PIT-079 模块裁剪）：

| 部分 | 大小 | 占比 |
|---|---|---|
| Windows 侧（x64）：`SysRecover.exe` 1.31 + `SysRecoverUI.exe` 2.14 + `libwim-15.dll` 0.47 | **3.92 MB** | **10.0%** |
| 救援层（内核 + initramfs + GRUB/shim，**与位数无关**）| **35.06 MB** | **89.8%** |
| 合计 | **39.06 MB** | 100% |

加 32 位后的增量：

| 方案 | 增加什么 | 增量 | 新 `dist` |
|---|---|---|---|
| **B**：x86 主体 + **x64 只做备份** | x86 全套（3.92MB）+ x64 **只留 CLI**（1.31+0.47），去掉 x64 GUI（−2.14）| **+1.8 MB** | **≈40.9 MB（+4.6%）** |
| **C**：两个完整版 + 启动器 | x86 全套 + x64 全套 + 启动器 | **+4.0 MB** | **≈43.1 MB（+10%）** |
| （对照）只出 x86 | 换成 x86 一套 | ≈0 MB | ≈39.0 MB |

> **救援层占了 93%，所以加一套 Windows 程序对总体积几乎没影响** ✓
> 下载包（zip）约再 +1~2 MB。

## 3. 速度（只有"备份"受影响）

备份 = 读盘 + **压缩** + 写盘；32 位的劣势只在压缩这一段，且取决于算法：

| 备份算法 | 瓶颈 | 32 位相对 64 位 |
|---|---|---|
| `--compress fast`（XPRESS，很快）| **磁盘** | **≈0~10%** 慢（几乎无感）|
| 默认 / `maximum`（LZX）| CPU 与磁盘各半 | **≈10~20%** 慢 |
| `--compress recovery`（LZMS，最省空间）| **CPU** | **≈20~35%** 慢 |

- **还原：0%** ✓（格式化 + apply 由 Linux 救援层完成，与宿主 exe 位数无关）
- 量级示例（30GB、SSD）：`fast` 3.5min → 3.6~3.9min；`recovery` 12min → 15min
- 用户结论：**15 分钟变 18 分钟可以接受** ✓
- ⚠️ 以上为**区间估计**，非实测（本机无 i686 工具链）；装好后可做 A/B 实测补真实数字

## 4. 实施前置条件（三样）

1. **i686-w64-mingw32 工具链**（另装一套 MinGW；用户侧）
2. **官方 32 位 `libwim-15.dll`**（wimlib 同时发布 `windows-i686` / `windows-x86_64` 包 ✓）
3. **Makefile `ARCH=x86` 分支**（我方；含 rc/manifest 的 x86 编译）
   - ⚠️ **两个 `libwim-15.dll` 同名，不能放同一目录** → 需分目录（如 `x64\`）或用启动器布局
   - 方案 B 需"32 位 GUI 起 x64 子进程做备份"，进度经 `progress.json` 轮询（机制已有 ✓）
   - 方案 C 更规整：两个完整 exe + 极小启动器按系统位数选择，**无跨进程**

## 5. 不受影响 / 注意点

- **救援层与宿主位数无关** ✓（Linux 侧照旧）
- **BIOS + GRUB4DOS** ✓ 与位数无关
- **UEFI 引导资产是 x64**（`shimx64.efi` + 64 位内核）→ 注意"**32 位 Windows 装在 64 位 UEFI 机器上**"
  是**普通情况** ✓，我们的资产照用 ✓；只有极罕见的 **32 位 UEFI（IA32）** 才需要 `shimia32.efi` + 32 位内核 ✗
- **PE**：32 位 PE 只能跑 x86 ✗ → 若做方案 C，启动器需能识别并选 x86；`fast` 压缩下速度差异很小 ✓
- VSS：32 位进程在 64 位系统上看不到 **64 位 VSS writer**，但我们只用**卷级快照**（不需要应用一致性）✓ 不受影响

## 6. 建议的落地方式

- 若 32 位客户占比不高 → **只出 x86**（一个包通吃，只亏备份那点速度）
- 若常备份大系统 + 64 位机器为主 → **方案 C**（两个完整版 + 启动器，比 B 少一层跨进程）
- 若 32 位客户几乎没有 → 维持 x64，并在**下载页/说明**里写明"仅 64 位"
