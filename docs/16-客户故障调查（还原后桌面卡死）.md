### 8.2 EA 修复全自动链路落地（0.6.38，2026-10-06，PIT-122/123）

**方案定稿**：Linux 侧直写 EA 被两组实验否决（`ntfs-3g user_xattr` 写出来的是 **ADS 流**不是 EA；真 EA 读不到、`system.ntfs_ea` 写被拒）→ 改为**首启补写**（Windows 的 `NtSetEaFile` 是唯一可行通道）：

1. **备份时**（全自动）：扫描源里带 EA 的文件（路径+名字+值）→ `eapack.dat`，连同补写器 `zj-ea-apply.exe` + 同步策略片段 `zj-regpol.bin` 打成子镜像 **`ZJEA`** 并入主镜像（单文件分发不变；无 EA 的系统完全无感）。
2. **还原时**：Windows 暂存从镜像内容发现 `ZJEA` → 契约 `ea_index`；救援层解包投放进目标 `C:\ZJRESTORE\ea\`，并安装**本地组策略启动脚本钩子**（`scripts.ini`/`gpt.ini`/`Registry.pol` 三件套，纯文件、免改注册表）。
3. **首次开机**：登录前、SYSTEM 身份自动跑补写器 → `NtSetEaFile` 写回全部 EA → 自清理（删钩子条目/包、延迟删除脚本与自身）→ 次轮开机不重跑。**全程用户零操作**。

**验证（全部由 AI 独自完成，无用户参与）**：单测 39 用例/259 断言；本机 e2e（backup→extract→ea-apply→`fsutil` 复查）；QEMU 演练 **9/9 PASS**（含 `ea subimage`/`ea: deployed` 断言 + 盘上字节级复核）；**真实 Win10 VM 首启 e2e 四轮**：预登录执行（`shell_started=no`）、**含 `System32\` 路径**的 EA 写回成功、清理全项完成、延迟删除生效、次轮不重跑。

**全链一次贯通（0.6.39）**：对**真实 Win10 系统镜像**（2.22GB WIM、**1677 个 EA 文件**——该测试系统自身就带大量 EA，与客户 804 个同性质）完成：冷备采集（EA 包 563KB）→ QEMU 救援层真实还原（5.5GB apply + EA 投放 + 对已有钩子文件的合并）→ 首启（预登录）**ok=1676 / missing=1（被备份排除的文件）/ failed=0** + 清理全项。**结论：用 0.6.38+ 新备份的镜像，"备份 → 暂存还原 → 首启自动补写"全链已打通并实测成功。**

**关键坑（已修，详见 PIT-123）**：gpt.ini 版本必须与注册表记录不同（否则 gpsvc 判"无变化"跳过）；`gPCMachineExtensionNames` 必须声明 Scripts+Registry 两个 CSE；没有 `RunStartupScriptSync`+`SyncForegroundPolicy` 同步策略就会在登录后才跑；**32 位补写器访问 `System32\GroupPolicy` 会被 WOW64 重定向到 SysWOW64**（进程级关闭重定向修复）。

**对客户的处置**：
- **旧镜像**（`20261005Win10.19044备份.wim`，EA 完好但无 ZJEA 子镜像）→ 两种路径：① **PE 就地还原**（Windows 侧 apply 原生保 EA，立即可用）；② 后续 `ea-repack`（从旧镜像在 Windows 上物化 EA 再打包，**尚未实现**）。
- **新备份起**：用 0.6.38+ 正常"备份 → 暂存还原"即可，EA 自动采集 + 自动补写；首启后右键/桌面是否恢复即最终因果验证。

**③ 定因（2026-10-07，用户确认"EA 修好后仍卡"后重新分析）——右键卡死 = 失效的右键菜单处理器，与 EA 无关**：

- **症状**（客户原话 10-05）："能使用，但**一点右键就打圈**；重启资源管理器后左键能用、**右键不行**"——**右键专属故障 = 右键菜单处理器问题**（不是系统整体/EA 问题；EA 已 902/902 写回成功）。
- **等待链**（客户 10-03 截图）：`explorer.exe (PID 976) 线程 1440 → explorer.exe (PID 976) 线程 5248` —— UI 线程等一个**卡住的 shell 工作线程**；转储里同见 `shell32→combase`（COM 激活处理器）路径上的阻塞线程。
- **唯一"注册了但 DLL 缺失"的处理器**（diag 标 `*** MISSING ***`）：`HKCR\*\shellex\ContextMenuHandlers\{A5AF131F-…}` → `C:\Users\Administrator\AppData\Local\Temp\DoubaoPortableTemp\doubao_ext\1.49.10\shellext.dll`（**豆包便携版从 Temp 注册的右键扩展；注册在 `*` = 对所有文件/文件夹右键都会加载**）。其余第三方处理器（火绒 HRShell、IDM、搜狗、蓝盾、酷呆、7-Zip、WinRAR、WPS）DLL 均在。
- **为什么我们的还原必然造成它损坏**：排除清单（`src/wim/exclude.cpp:35`）明确排除 `\Users\*\AppData\Local\Temp*` → **该 DLL 不进镜像**；而注册项随注册表（SOFTWARE hive）原样还原 → "有注册、无 DLL"的坏处理器 → 每次右键都尝试加载它 → 打圈/卡死。
- **为什么易数等工具不卡**：易数/DiskGenius 是**扇区/整分区级**（Ghost 式）还原 → Temp 原样保留（DLL 还在）→ 处理器完好。**"只有我们还原后卡"的差异完全吻合**。

### 10. 2026-10-07 复测（0.6.47）：清理仍失效的真根因 = WOW64 视图 + 跨 hive 组合（PIT-134，`0.6.49`）

**③ 实验室复现（把两类组合都打出来）：** 注入"用户 hive 64 位视图 + 跨 hive"组合（处理器 `HKLM\…\*\shellex\…\{…}`、CLSID 在 `HKCU\Software\Classes\CLSID\{…}`，64 位写入）→ 旧补写器 **`found=0`**（两个都漏）；修一半（只改用户根双视图）→ `found=1`（用户 CLSID 找到、HKLM 处理器因跨 hive 解析仍漏）；全部修完 → `found=2 cleaned=2` ✓。逐层定位两个真 bug：

- **bug ② `ResolveClsid` 只在本 hive 解析**：处理器与 CLSID 分处不同 hive（便携软件常见）时双双漏掉；而 `diag` 用 HKCR 合并视图能看到 → **"诊断标 MISSING、清理不动它"**。

**④ 修复（`0.6.49`）：** `ScanUserRoot` 类相关部分 64/32 双视图各扫一遍（清理端按 display 去重）；`ResolveClsid` 跨 hive + 各视图（本根→HKLM 双视图→HKCU→所有已加载用户 hive）。**实验室验证**：注入组合 → 新补写器 `refs: removed HKLM\…\{…}` + `refs: removed HKU\S-1-5-…\CLSID\{…}\InprocServer32`、`found=2 cleaned=2`、两条 `reg query` 均"找不到" ✓。⚠️ 对客户而言**生效的关键是双视图**（他们的两个键都在用户 hive 64 位视图）；跨 hive 解析是同类组合的加固。
